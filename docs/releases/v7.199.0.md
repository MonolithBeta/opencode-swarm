# Delegation gate: configurable acceptance criteria auto-injection

## Summary

- Adds the opt-in `hooks.auto_inject_acceptance` setting (default: `false`).
- When enabled, a `coder` or `reviewer` delegation that has no `ACCEPTANCE:` line, or only an empty one, is no longer rejected with `ACCEPTANCE_FIELD_REQUIRED`. The gate writes a generic default requirement into the dispatch, marked `(auto-injected default: ...)`, and queues an `ACCEPTANCE AUTO-INJECTED` advisory for the dispatching session (when that session is registered).
- With the default (`false`), the existing strict fail-closed behavior is unchanged.

## Changes

- Adds `auto_inject_acceptance` to `HooksConfigSchema` in `src/config/schema.ts` and `opencode-swarm.schema.json`.
- `createDelegationGateHook` in `src/hooks/delegation-gate.ts` fills an empty `ACCEPTANCE:` header in the field that actually carries it (line endings preserved), or appends a block to `prompt` (else the first text field). It never fabricates a field: if the dispatch has no text field at all, the strict rejection stands. The signal is emitted only after the injected text passes the same validator.
- `config doctor` now derives its known-hook allowlist from `HooksConfigSchema`, so the new key (and the previously missing `background_subagents` and `background_pending_timeout_minutes`) is no longer reported as an unknown hook field that `--fix` would remove.
- Documents the setting in `docs/configuration.md`.
- Adds tests: `tests/unit/hooks/delegation-gate-acceptance-autoinject.test.ts` (injection, preservation, flag-off, field targeting, CRLF/NBSP, advisory) and `tests/unit/services/config-doctor-hooks-parity.test.ts`.

## Known caveats

- The injected requirement is generic, not task-derived. For a single task mapped to spec requirements the verbatim `FR-###`/`SC-###` text is still appended and coverage-checked, but an unmapped task or a multi-task phase/council reviewer dispatch only receives the generic line.
- Project config can set this key (as it can `hooks.delegation_gate`); it has no user-level-only protection.
- The motivating OpenCode v2 behavior (a hook-thrown rejection not being rendered to the model) is not verifiable in this repository.

# Guardrails: `authority.enabled: false` no longer rejects custom or host agents as unknown

## Summary

- With `authority.enabled: false`, writes by agents that the plugin has no authority classification for (for example custom host agents such as `sre-planner`, `builder` or `infra`) were rejected with `AUTHORITY_UNKNOWN_AGENT` ("Unknown agent: no authority classification exists"), even though authority enforcement had been switched off.
- Root cause: in `checkFileAuthorityWithRules` the unknown-agent denial ran for every agent regardless of `authority.enabled`, and `buildEffectiveRules` returns only the built-in role rules while authority is disabled.
- Fix: while authority is disabled, an agent without a classification is no longer denied merely for being unknown. It still passes through the hard-policy checks first and is then allowed.

## Behavior change

- This applies only when you set `authority.enabled: false`. The default (`true`) is unchanged: unclassified agents are still denied with `AUTHORITY_UNKNOWN_AGENT`.
- While authority is disabled, these checks still apply to every agent that reaches them: path safety and workspace containment, the configured `authority.universal_deny_prefixes` (empty by default), the canonical read-only and dedicated-tool-only roles, the coder `.git`/`.swarm` protection, and verifier-config protection for the built-in swarm roles.
- Newly admitted (unclassified) agents are additionally denied writes to `.git/` and `.swarm/` with `AUTHORITY_PROTECTED_PATH` when they use the file-write tools (write, edit, patch). Shell-command writes keep following the existing shell-path rules, which are unchanged. They remain able to write other workspace paths, including verifier and CI configuration, because the built-in host agents (`build`, `general`) already could. Set `authority.universal_deny_prefixes` (for example `.opencode/`, `.github/workflows/`) to keep further paths protected.
- Per-agent `authority.rules` (including `readOnly`) are still not applied while authority is disabled, exactly as before.
- The literal agent name `unknown` (a session registered without an agent name) keeps being denied with `AUTHORITY_UNKNOWN_AGENT` even while authority is disabled.

## Changes

- `checkFileAuthorityWithRules` (`src/hooks/guardrails/file-authority.ts`) treats an unclassified agent as allowed-through when `authorityEnabled === false`, after universal deny, control-state protection and the other hard-policy checks.
- Adds unit coverage in `tests/unit/hooks/guardrails-authority-disabled-hook-feedback.test.ts` for the disabled-mode allow, the retained denials, and the unchanged decision codes and layers.

# Native agents keep their identity across the swarm plugin (v1 + v2)

## What

Sessions whose primary agent is one of OpenCode's built-in agents (Build,
Plan, general) are no longer silently re-labelled `architect` by the swarm
plugin, on either the v1 or the v2 host. Build and Plan keep their own file
authority, receive no architect-only directives (ARCHITECT WORKFLOW REMINDER,
`[NEXT]` delegation directive, guardrail/knowledge/PLANNING PROFILE
injections), and are no longer subject to the swarm-only in-session
full-test-suite block. Explicit architects, `auto_select_architect` default
architects, and the subagent-identity repair keep today's behavior exactly.

## Why

Several code paths overwrote or inferred the session identity as `architect`
without asking who the primary agent actually is, defeating the earlier
per-surface native-agent exemptions (#559, #942, #808). The fix introduces a
per-session PRIMARY-owner record (`getPrimaryOwner` / `isSwarmOwnedSession` /
`isRegisteredSwarmSubagent` in `src/state.ts`) and restores it at every
handoff: the Task-completion handoff and the delegation tracker's no-agent
branch restore `primaryOwner ?? architect`; the stale-delegation revert now
applies only to registered swarm subagents; v2 message views stamp
`info.agent` on USER views, and the pipeline-tracker / delegation-gate message
stages resolve identity through the shared
`resolveMessageTransformContext` (also fixing prefixed architects —
`mega_architect` — never receiving the workflow reminder, and treating the
`unknown` placeholder identity as unmapped so first-turn architect sessions
keep their guidance); the full test-suite block is scoped to swarm-owned
sessions (destructive-command, containment, and symlink checks stay universal;
the Task-to-coder ACCEPTANCE gate stays target-keyed); sessionless
`system.transform` calls (title, summary, agent generation) emit no
swarm-specific system text, including the swarm-command-rule banner and the
sessionless HF-1b emission.

## Deliberately updated pinned tests

Two pre-existing suites pinned the OLD sessionless behavior and are updated
under the issue's replacement discipline (replaced, not weakened; each new
assertion pins the replacement contract):

- `tests/integration/system-transform-global-mode-fallback.test.ts` — its
  three sessionless cases asserted borrowing another session's TURBO/FULL-AUTO
  flags and the PLANNING PROFILE producer; they now assert the new
  no-swarm-text contract with byte-exact equality. Independently pinned by the
  new `system-transform-sessionless-no-swarm-text.test.ts`.
- `tests/unit/hooks/system-enhancer-hf1b-adversarial.test.ts` (ATTACK 7) —
  pinned a sessionless HF-1b emission; sessionless surfaces execute no tools,
  so the guard's protective value there was nil. ATTACK 7 now asserts the
  sessionless call emits nothing. Session-bound HF-1b behavior is unchanged
  (ATTACK 1-6).

## Known caveats

- The primary-owner record is in-memory: after a plugin restart an unmapped
  session keeps today's architect-default behavior until its next
  chat.message / v2 seeding event (documented out of scope in #3320).
- A v2 plan/build session's very first `prompt` event (before any context
  event records its owner) still follows today's behavior until the next
  seeding event.
- With `auto_select_architect` enabled, an agent-less turn IS the default
  architect taking over — it re-arms the primary owner to `architect`. A
  session that ran one native-agent turn and then returns to agent-less
  default turns is an architect session again (per that option's own
  semantics).
- Message-view identity stamping is USER views only (the v1 SDK shape carries
  `agent` on `UserMessage`, never on `AssistantMessage`), so role-unfiltered
  consumers keep matching user-authored turns only.
- `/swarm memory` instruction-pairing can still re-stamp a session identity
  to architect — same defect class, separate surface, filed as #3372.

No migration required.

# Host v2: preserve host-provided agent across tool hooks and Task handoffs

## Summary

- On OpenCode v2 hosts, `onV2ToolBefore` and `onV2ToolAfter` supply the authoritative host-verified `agent` on every tool hook and seed session state via `seedV1SessionState`.
- Previously, `seedV1SessionState` did not refresh `session.lastAgentEventTime` when re-seeding an existing session with the same agent name, and `tool.execute.before` evaluated the v1 10-second `staleDelegation` heuristic (`!session.delegationActive && Date.now() - session.lastAgentEventTime > 10000`) even when `input.agent` was explicitly provided by the v2 host. For non-`architect` agents with `delegationActive === false`, this overwrote `activeAgent` and `session.agentName` to `'architect'` for one tool call every 10 seconds, allowing a hard-limit circuit breaker (`hardLimitHit === true`) to be bypassed intermittently.
- Additionally, `tool.execute.after` Task handoff unconditionally restored `ORCHESTRATOR_NAME` (`'architect'`) instead of preserving a host-provided parent `input.agent`.

## Changes

- Refreshes `session.lastAgentEventTime` in `seedV1SessionState` (`src/host/v2/setup.ts`) whenever a valid v2 agent reference is seeded.
- Guards the v1 `staleDelegation` fallback in `src/index.ts` `tool.execute.before` so it only runs when `input.agent` is not explicitly provided by the host.
- Restores `readHostAgent(input) || ORCHESTRATOR_NAME` (the trimmed host agent, else `architect`) during `tool.execute.after` Task handoff in `src/index.ts`, and seeds `activeAgent` from the host agent in `tool.execute.before` when it is unset.
- The two call-site casts in `src/index.ts` are replaced by one typed helper (`readHostAgent`) that trims the host agent name and cannot throw on a non-string agent. `normalizeV2AgentRef` is intentionally unchanged (it returns the host name verbatim) so a padded name cannot resolve to an architect-capable identity on the architect-only tools path.
- The fix applies only when the host sends the agent on tool hooks (OpenCode v2); hosts that do not (v1) keep the previous stale-delegation behaviour unchanged.
- Adds regression tests in `tests/unit/host/v2/adapter-behavior.test.ts` and `tests/unit/host/v2/adapter-behavior-host-agent.test.ts`.

# Skill frontmatter hardening: stamp anchoring, flow-map handling, generated-tree convergence (#3215, #3216, #3217)

## What changed

- The `swarm-contract-digest` stamp reader no longer resolves stamp-shaped text that sits
  inside a YAML block scalar (`description: >` / `|` continuations). The two-space
  metadata-child stamp form is only accepted inside a real `metadata:` block; the legacy
  column-0 form is unchanged. A spoofed digest can no longer shadow or impersonate a
  skill's contract stamp in drift-check staleness findings (#3215).
- An inline flow-map `metadata:` value (`metadata: {audience: swarm-plugin}`) is now
  resolved by the frontmatter reader exactly like the block form — a skill whose audience
  is declared that way is constrained by it instead of silently matching every project
  and runner (the previous absent/match-all fail-open). Malformed flow values fail
  closed (audience invalid, no match) (#3217).
- The skill reviser rewrites any inline-valued `metadata:` line to the canonical block
  form when bumping a version — a revision can no longer emit a second `metadata:` block
  beneath a legacy inline one (#3217).
- The 13 generated skills that still carried a legacy top-level `triggers:` list are
  migrated to the generator's own emission shape (`triggers` as the first
  `metadata:` child, a single-quoted JSON array string), and one generated skill whose
  directory name did not match its `name:` field is renamed to match — the directory
  now carries the generator's `sanitizeSlug` output including its trailing hyphen
  (64 characters; the pre-existing `name:` field and body self-reference already used
  that form) (#3216).
- The drift-check `skill-frontmatter` detector now enforces the generated tree
  (`.opencode/skills/generated/`) — hand-edits reintroducing non-spec top-level keys or
  name mismatches there fail `bun run drift:check --enforce` — and flags non-empty
  inline `metadata:` values as non-canonical. Only the audience detector keeps its
  generated-tree skip (#3216, #3217).

## Why

All three residuals came from the PR #3207 review: the bounded frontmatter parser was
used statelessly or shape-blindly at four sites, so YAML shapes other than the writer's
canonical block form were mis-read (spoofed stamp accepted, audience constraint
dropped), mis-written (duplicate `metadata:` key), or invisible to CI (a whole tree
exempt from the conformance detector).

## Verification

- New regression suites: `skill-contract-digest-block-scalar-3215.test.ts` (its
  block-scalar spoof assertions are RED at base), `skill-frontmatter-flow-forms-3217.test.ts`
  (flow-map and reviser assertions RED at base, block-form controls green),
  `generated-triggers-convergence-3216.test.ts` (RED at base: 13 legacy files; also pins
  name === directory), and `generated-triggers-migration-shape-3216.test.ts` (migration
  shape parity with the generator's `yamlJsonString` emission — its shape oracle is green
  at base by construction; the companion 13-file declaration test carries the RED leg).
  The feedback round adds a battery for the multi-line flow, quoting, and stamp-writer
  surfaces in `skill-frontmatter-feedback-3387.test.ts`.
- Preserving floors green: the #2907 transition matrix, skill-audience suite,
  skill-generator suites, skill-reviser suite, and the stamp script (all four shipped
  stamp forms still verify).
- `bun run drift:check --enforce` exit 0 with the exemption removed and the tree
  converged.

# PR-Review: typed terminal classes on failed verdict lanes; typed-dead N-of-M settlement

## What

Every failed reviewer/critic verdict lane now carries a durable, typed terminal
class, and an item whose owner lanes all died with a typed terminal — not only
host-liveness deaths — can settle through N-of-M verdict settlement as a
disclosed, downgrade-only INCOMPLETE once the per-item retry budget
(`1 + PR_REVIEW_VERDICT_RETRY_BUDGET` attempt batches) is exhausted (#3275
RC3).

- New `verdict_contract` failure class: verdict-lane collection-validation
  failures (any predicate, keeping the `PR_REVIEW_VERDICT_CONTRACT_INVALID`
  error code) and transport-validation throws settle `error` with
  `workflowLaneFailureClass: 'verdict_contract'` for
  `swarm-pr-review:reviewer|critic` lanes. PR-feedback lanes keep their
  classless terminals; base/micro discovery keeps `contract`.
- Provider-terminal settlements that end `error` (never the aborted →
  `cancelled` arm) are typed `resource` for every lane, mirroring the #2615
  launch-rejection rule. A base dimension whose only failure is such a lane now
  derives FAILED/`resource` (also for pre-upgrade classless records carrying
  `terminalErrorClass`) and admits into partial base coverage instead of
  throwing "lacks a typed terminal failure"; under staged resilience it
  surfaces as a bounded `resource` retryable remainder.
- N-of-M admission accepts `verdict_contract`, `resource` and legacy
  `contract` verdict-mode owners as typed-dead evidence (legacy `contract`
  discloses as `verdict_contract`); a completed-but-unclaiming owner counts as
  a consumed attempt instead of a permanent blocker. A missing record,
  classless silence, `operator_cancelled` (default decision) and an aborted
  host cancellation still block — nothing widens identity, nothing admits
  silence, and no path yields APPROVE or a synthesized verdict.
- The settlement receipt now discloses the TRUE class per item
  (`liveness_dead`/`verdict_contract_dead`/`resource_dead`); old
  `liveness_dead` receipts keep parsing.
- Ghost-owner prevention: reviewer/critic dispatches validate every lane agent
  BEFORE the validation batch is recorded, and a dispatch that launches zero
  lanes rolls the batch back — a declared owner with no delegation record can
  no longer be created.
- Micro dead-family disclosure admits `resource`-class and pre-upgrade
  classless provider-terminal micro lanes under the same exhausted-budget
  rule; `operator_cancelled` and silence stay rejected.
- The reviewer/critic BLOCKED message now carries per-item attempt counts
  (`attempts: <used> of 3`, `remaining: <n>`) and names the blocking owner
  class; the unreachable "controller-observed liveness evidence" advice is
  gone. `pr_workflow_status` exposes the same counts as
  `prReviewProjection.verdictAttempts`.

## Why

Verdict lanes that failed for contract or provider reasons could never settle:
the admission predicate read exactly one class (`liveness`), the producers
stamped none, and the only exits were aborting the review or human
intervention — the #3275 wedge. Together with #3310 (which removed the
prompt-collision trigger), retries can now succeed, and persistent non-liveness
failures degrade honestly instead of wedging.

## Notes

- The gate's architect-parent repair predicate (base/micro lanes) is
  deliberately unchanged and stays strictly liveness-gated.
- `operator_cancelled` owners remain non-admissible by default (issue #3311
  AC13): an architect cancelling idle lanes must not convert unvalidated
  candidates into disclosed-dead evidence by its own act.
