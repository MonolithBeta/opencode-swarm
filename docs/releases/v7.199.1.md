# Guardrails: allow file authority within linked git worktrees

## Summary

- When executing agent sessions inside a Git worktree or inspecting files across worktrees of the same repository, file authority checks could incorrectly fail with `AUTHORITY_ROOT_ESCAPE` (`target resolves outside the working directory`).
- Root cause: `checkFileAuthorityWithRules` assumed all valid file paths must be strictly contained within `dir` (`cwd`). In multi-worktree workflows, worktrees of the same repository live in sibling directories outside `dir`.
- Fix: `checkFileAuthorityWithRules` now discovers linked worktrees via `git worktree list --porcelain` (cached in LRU with a 60 s TTL) and treats files located within any valid linked worktree of the repository as workspace-contained.

## Changes

- Adds bounded discovery: `getLinkedGitWorktrees(dir)` with LRU cache (60 s expiry, so worktrees created or removed mid-session — and transient git failures — are re-queried), a 1500 ms timeout, explicit byte bound, `windowsHide`, and `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`/`GIT_COMMON_DIR` stripped from the subprocess environment.
- Worktree roots are validated before they can widen containment: `bare` records are skipped, and every linked root must back-anchor to this repository — its `.git` file must reference a registration under this repository's `.git/worktrees/` whose own `gitdir` entry names the root back. This rejects registrations whose target has no cooperating `.git` pointer and registrations naming other repositories. Scope: worktree trust remains git-native trust — a target directory holding a `.git` pointer left by earlier git history (moved, copied, or pruned worktree folders) still validates, because git itself cannot distinguish that from a real `git worktree add`; sessions inside a bare clone's linked worktree get no trusted roots (fail-closed, same as before this change).
- Re-roots to the LONGEST (most specific) matching worktree root, so deny rules resolve against the right root in nested layouts.
- On Windows, worktree roots and targets are canonicalized through the native realpath (expanding 8.3 short-name forms such as `RUNNER~1` and stripping the `\\?\` device prefix) before containment comparison; write targets that do not exist yet are canonicalized via their nearest existing ancestor so not-yet-created files inside a linked worktree still match.
- A re-rooted target whose ancestor chain crosses a symlink/junction inside the matched worktree is denied (`AUTHORITY_ROOT_ESCAPE`), closing the new-file-write redirect path.
- Declared scope for coders is evaluated once, in the re-rooted coordinate system (the raw-path second evaluation is removed).
- Unit coverage in `tests/unit/hooks/guardrails-worktree-authority.test.ts` (sibling-layout allow/deny paths) and `tests/unit/hooks/guardrails-worktree-containment-hardening.test.ts` (cooperating and non-cooperating forged registrations, bare repositories, longest-match re-rooting, planted symlinks). Repository content that a trusted worktree's own scripts invoke (hook scripts, build steps) remains subject to the repository's own policies, as at base.

## Known caveats

- The worktree-root cache expires after 60 s; within that window a worktree added or removed mid-session is not reflected.
- Discovery runs a bounded synchronous `git worktree list` on the guard path for targets that escape `cwd` containment (at most once per directory per 60 s).

# Retry-escalation wedge gains a one-step audited repair (TASK_RETRY_USER_ESCALATION_REQUIRED while in_progress)

## What

A task whose coder retry ladder reached its durable `user_escalation` rung
refused every further coder dispatch with `TASK_RETRY_USER_ESCALATION_REQUIRED`,
and the remedy the message named — "authorize repair" — was itself refused
(`TASK_REPAIR_NOT_BACKWARD`) for the only plan status the wedged task can have
(`in_progress`). No documented, audited exit existed for the combination.

- The audited force repair (`update_task_status` with `status: "in_progress"`,
  `force: true`, exact CAS fields, `target_state: "idle"`, reason, and
  transition id) is now admitted exactly when a durable `user_escalation` exists
  for the task's CURRENT retry epoch and `retryCount` sits at the threshold —
  the ladder's own durable escalation record (machine-written when the ladder
  reaches its rung; user authorization arrives via the repair's audited
  `reason`). The task's plan status must already be `in_progress`; a wedged
  task still `pending` in the plan takes one ordinary `in_progress` status
  update first. `repair_idle` then reopens the task and
  clears the whole retry circuit (`retryCount`/`retryHistory`/`retryEpoch`
  reset, generation rotated), so the next coder dispatch starts fresh.
- Every other `in_progress` repair still fails closed with
  `TASK_REPAIR_NOT_BACKWARD`, and an unreadable escalation index fails closed
  with the new typed `TASK_REPAIR_ESCALATION_INDEX_UNREADABLE` (remapped like
  the sibling audit-index errors) instead of guessing admission.
- The `TASK_RETRY_USER_ESCALATION_REQUIRED` message now names the reachable
  action (the `update_task_status` force repair with its CAS fields) instead of
  the unreachable bare wording; the `update_task_status` schema descriptions
  and force-override log line no longer call the repair "backward-only".
- Docs: the recovery runbook gains a retry-escalation user-decision wedge
  section (covering the plan-status precondition, why
  `approve_retry_sounding_board` is scoped to the earlier rung, what
  `recover_rework_task` does and does not exit, and the superseded blocked
  round-trip workaround); the reset-session retry-gate disclosure,
  plan-durability, and engineering-invariants FR-005 entries name the new
  admission.

## Why

The repair machinery already carried every required property (CAS, PREPARED →
COMMITTED WAL, audit event, generation rotation, retry-circuit reset); only the
admission guard excluded the one state the escalation ladder itself creates,
leaving users with no verified supported recovery path.

## Verification

  (with `generation ≠ retryEpoch`), fail-closed partial-ladder/foreign-epoch/
  below-threshold refusals, guard order, and the index remap.
- `tests/unit/tools/update-task-status-escalation-wedge-3389.test.ts` —
  handler-level repair, circuit cleared, post-repair dispatch admission, the
  remedy-naming message pin, and the schema-wording pin.
